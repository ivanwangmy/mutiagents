# AI 智播课堂——项目总控开发规范

你现在担任本项目的技术负责人、架构师和全栈开发工程师。

请从零开始开发一个名为「AI 智播课堂」的拟人化多智能体教学互动平台。

本项目不是普通 AI 聊天网站，也不是简单地为三个大模型设置不同角色名称，而是一个能够让多个具有独立人格、知识、记忆和行动能力的 Agent 在同一课堂空间中自主互动的多智能体系统。

## 一、产品定位

产品名称：AI 智播课堂。

核心目标：让用户通过向一个或多个 Agent 提问，体验真实的多智能体课堂互动。

第一阶段只开发多智能体提问、回答、讨论和协作能力。

暂不开发：
- PPT 上传、解析和加载。
- 课程资料批量导入。
- 课堂录制、语音和视频。
- 作业管理和课程管理。
- 学习进度和学情分析。
- 教师端、学生端复杂权限系统。
- 支付和社交功能。
- 非必要的登录系统。

但是，系统架构必须为未来扩展课程知识库、PPT 理解、课堂语音和教师控制等能力预留合理接口。

## 二、固定 Agent

第一版只允许存在以下三个 Agent：

1. Alex：教师型 Agent。
2. Mia：助教型 Agent。
3. Ethan：学生型 Agent。

每个 Agent 必须具有：
- 独立身份和人格。
- 独立 System Prompt。
- 独立 Agent 配置。
- 独立 Skills。
- 独立工具权限。
- 独立运行状态。
- 独立长期记忆空间。
- 独立执行日志。
- 稳定的表达风格和决策特征。

禁止仅通过修改同一个模型的角色名称来伪装多 Agent。

允许底层使用相同模型供应商，但每个 Agent 必须具有独立的运行上下文、人格配置、消息身份、记忆 namespace 和权限边界。

## 三、Agent 自主性

用户可以选择一个、两个或三个 Agent。

selected_agent_ids 是强制参与者边界。

任何未被选择的 Agent 都不能自动加入。

Agent 必须能够根据上下文自主决定：
- 是否发言。
- 是否回应其他 Agent。
- 是否向用户追问。
- 是否提出质疑。
- 是否补充知识。
- 是否请求其他 Agent 协助。
- 是否调用工具。
- 是否等待其他 Agent。
- 是否结束本次讨论。

禁止固定轮流发言。

禁止为了制造热闹而生成无意义消息。

禁止要求每个 Agent 对每条消息都必须回应。

## 四、真实多智能体交互

必须实现真实的 Agent Message Bus。

消息类型至少包括：
- message
- question
- response
- challenge
- request_help
- handoff
- conclusion

Agent 必须能够读取任务中允许共享的公开消息，并针对具体内容回应。

共享当前对话上下文不等于共享私人长期记忆。

必须隔离各 Agent 的长期记忆空间。

## 五、技术架构

前端：
- React
- TypeScript
- Vite
- Tailwind CSS
- shadcn/ui

后端：
- Python 3.11+
- FastAPI
- Pydantic
- SQLAlchemy 2.x
- LangGraph

数据：
- PostgreSQL
- LangGraph 官方 PostgreSQL Checkpointer
- LangGraph Store
- Alembic

通信：
- REST API
- SSE 实时事件

部署：
- Docker Compose

必须先检查运行环境、依赖兼容性和官方文档。

不允许凭空假设某个包的 API。

不允许在 FastAPI 主进程中直接使用裸 exec 执行用户代码。

## 六、模型接入

使用统一模型适配层。

模型 API Key 必须通过环境变量管理。

必须区分：
- 普通文本生成。
- 流式文本生成。
- 原生 Tool Calling。
- 结构化输出。

不得将模型生成 JSON 误认为真实工具调用。

如果模型或供应商不支持原生 Tool Calling，必须明确说明并提供兼容方案，不得伪造工具执行成功。

## 七、拟人化要求

拟人化不等于增加语气词、表情包和动画。

真正的拟人化必须体现在：
- 不同的知识组织方式。
- 不同的判断习惯。
- 不同的提问方式。
- 不同的观点倾向。
- 不同的表达节奏。
- 对其他 Agent 的持续认知。
- 长期互动中稳定的人格表现。

三个 Agent 在面对相同问题时，应当表现出有依据的思维差异，而不是简单替换措辞。

## 八、前端设计原则

用户提供的参考截图是主要视觉依据。

整体采用双栏式智能课堂空间：
- 主区域：课堂讨论与消息展示。
- 侧边区域：Agent 头像、角色资料和运行状态。
- 顶部：产品导航和当前对话信息。
- 底部：提问输入框和讨论控制。

具体布局允许根据可用性调整，但必须保留双栏式课堂体验。

视觉风格：
- 现代、简洁、轻量。
- 白色和浅灰色为主。
- 低饱和度紫色作为品牌强调色。
- 统一头像风格。
- 适度圆角和留白。
- 避免过多渐变、阴影和复杂装饰。
- 桌面端优先，兼容移动端。

Agent 头像必须使用正式静态素材，不允许随机生成头像或用字母代替正式头像。

## 九、真实执行原则

所有前端状态必须来自后端真实数据。

所有 Agent 消息必须由实际模型运行生成。

所有工具调用必须经过真实的后端工具执行链路。

所有实时状态必须由真实后端事件驱动。

禁止：
- 假消息。
- 假工具调用。
- 假思考动画。
- 固定脚本模拟多 Agent 对话。
- 前端定时器模拟 Agent 活动。
- 仅修改按钮状态冒充任务暂停或恢复。

不得展示模型内部思维链，只展示公开发言、行动摘要、工具调用和执行状态。

## 十、安全要求

- API Key 不得写入前端代码。
- 敏感配置不得提交 Git。
- 对工具执行实施权限控制。
- 对用户输入、文件内容和外部检索结果进行提示词注入防护。
- 对工具设置超时、调用次数和资源限制。
- Python 执行必须使用真正隔离的沙箱服务。
- 高风险外部操作必须经过用户确认。

## 十一、开发纪律

必须按照本项目的 0—11 轮提示词顺序执行。

每轮只实现当前阶段的任务。

每轮开始前：
1. 检查当前项目状态。
2. 阅读已有架构和代码。
3. 确认本轮依赖。
4. 制定实施计划。

每轮完成后：
1. 列出新增和修改的文件。
2. 说明实际实现的功能。
3. 运行相关测试。
4. 给出测试结果和证据。
5. 列出尚未完成的内容。
6. 列出下一轮需要的准备事项。

如果测试未通过，不得宣称完成。

不要为了完成当前阶段而破坏此前已经通过测试的功能。

用户不熟悉编程，请用清晰的中文说明开发进展、运行方式和操作步骤。

未经用户确认，不得擅自改变产品定位、技术栈或增加第四个 Agent。

现在请始终将本规范作为整个项目的最高开发约束。
